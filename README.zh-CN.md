# SSE Lens

[English](./README.md) · **简体中文**

一个 Chrome 扩展，把**当前标签页**的 Server-Sent Events 渲染成可读的侧边栏内容：分帧事件、JSON 树、重组后的 LLM 增量文本，以及原始字节。

做它的原因很简单：DevTools 的 Network 面板把 SSE 显示成一坨不断变长的 `data:` 文本。技术上完整，实际上没法读——尤其是逐 token 返回的 LLM 流，你真正想看的东西（那个回答）被摊在了四百个帧里。

---

## 什么场景下需要它

| 场景 | DevTools 给你的 | SSE Lens 给你的 |
| --- | --- | --- |
| **调试 LLM 应用**——到底是模型返回得不对，还是你的客户端拼错了？ | 400 行 `data:`，靠眼睛读 | 拼接好的完整回答，并标出它取自哪个 JSON 路径，让你能核对 |
| **流到一半就断了** | 一个"就这么结束了"的响应 | 断在哪里、最后一帧是否完整、尾部到底剩了哪些字节 |
| **"curl 能跑，浏览器里不行"** | 两个没法对比的东西 | 从真实请求生成的、可直接运行的 `curl` 复现命令 |
| **客户端一个事件都没收到** | 不告诉你为什么 | 帧是到了但格式不对，还是根本没到——`content-type` 写错会立刻显现 |
| **推理模型返回两路文本** | 两路混在一起 | 区分 `content` 与 `reasoning_content`，不会把思考草稿当成答案 |
| **提 bug 报告** | 截图 | JSON / NDJSON 导出，并附带"哪些内容被脱敏或丢弃"的说明 |

典型用户：对接 OpenAI / Anthropic / Gemini / Ollama 或自研网关的开发者；做聊天界面、实时看板、进度推送、消息通知流的开发者。

**不适合用它做：** WebSocket、普通（非流式）REST、以及重放或修改请求。见 [能力边界](#能力边界)。

## 功能

| 能力 | 说明 |
| --- | --- |
| 事件时间线 | 每一帧的 `event`、`id`、`retry`、注释，以及相对流开始的时间偏移 |
| 全部展开 / 收起 | 一次点击展开或收起所有已加载的帧**以及**帧内的 JSON 树 |
| JSON 树 | 逐帧可折叠，常见结构默认展开 |
| 增量合并 | 拼接增量文本，并**标明它来自哪个字段**，让推断结果可核对 |
| 原始文本 | 精确的原始字节，用于排查分帧本身的问题 |
| 请求详情 | 请求头、请求体，以及可直接运行的 `curl` 复现命令 |
| 导出 | JSON 或 NDJSON，均附带脱敏与丢弃说明 |
| 双语 | English / 简体中文，跟随浏览器或手动指定 |

可抓取 `fetch`、`XMLHttpRequest` 和 `EventSource`，覆盖主框架与 iframe。

## 安装

需要 **Chrome 116+**（侧边栏 API）和 [pnpm](https://pnpm.io/)。

```bash
git clone git@github.com:dcc123456/sse-lens.git
cd sse-lens
pnpm install
pnpm build
```

然后在 Chrome 中：

1. 打开 `chrome://extensions`
2. 打开右上角的**开发者模式**
3. 点击**加载已解压的扩展程序**
4. 选择 **`dist/`** 目录——不是项目根目录

> 每次执行 `pnpm build` 之后，都要点一下 SSE Lens 卡片上的 **↻ 刷新**图标。否则 Service Worker 的改动不会生效。

## 使用步骤

### 1. 打开侧边栏

点击工具栏上的 SSE Lens 图标。侧边栏会在右侧打开，并自动跟随你当前查看的标签页——不需要手动选择页面。

### 2. 刷新你要检查的页面

**这一步很关键，跳过它是"什么都看不到"最常见的原因。** 钩子必须在页面脚本取得 `fetch` 引用**之前**完成替换。而你安装扩展或打开侧边栏时已经打开的页面，其脚本早就跑完了。原因见[为什么必须刷新](#为什么必须刷新)。

### 3. 触发流式请求

正常使用应用即可——发一条聊天消息、打开看板。流会在开始时出现在侧边栏里。

### 4. 阅读

| 标签页 | 用途 |
| --- | --- |
| **Events** | 逐帧时间线；展开任意一帧可看它的 JSON 树 |
| **Merged** | 拼接后的文本，并标明取自哪个 JSON 路径 |
| **Raw** | 原始字节，当你怀疑分帧本身有问题时看这里 |
| **Request** | 请求头、请求体，以及可复制的 `curl` 命令 |

要提 bug 就用 **Export**。**⚙** 标签里可以设置语言、抓取开关、额外要脱敏的请求头，以及各项体积上限。

### 排查

| 现象 | 原因与处理 |
| --- | --- |
| 侧边栏提示该页面无法检查 | 你在 `chrome://`、应用商店或其他扩展的页面上。Chrome 禁止扩展在这些页面运行，请切换到普通 `http(s)` 页面。 |
| 流跑起来了但什么都没出现 | 在侧边栏已打开的状态下刷新页面（第 2 步）。 |
| 重新构建后仍然没有 | 到 `chrome://extensions` 点 SSE Lens 卡片上的 **↻**。 |
| `EventSource` 看不到注释和心跳 | 这是预期行为，界面上也有标注——那些字节在钩子能看到之前就已被浏览器消费掉了。见[不同传输方式的保真度](#不同传输方式的保真度)。 |
| 长流看起来被截断 | 这是窗口化与配额限制。被丢弃的帧一定会**计数并明确显示**，绝不静默省略。 |

## 没有真实 API 也能试

本地服务器复现了每一条抓取路径，包括那些公开接口不会按需给你的情况——错误标注的 content-type、在事件中间被截断的流、主动 abort：

```bash
pnpm demo      # http://127.0.0.1:8787/
```

在侧边栏打开的状态下访问该地址（记得刷新一次），然后点击页面上的按钮。有两个用例值得专门确认：**plain JSON** 必须**不**出现在侧边栏里；**fidelity** 用于验证钩子重建响应之后，页面收到的仍是正确、完整的响应。

如果要用真实的 socket 字节校验解析器，在服务器运行的情况下执行：

```bash
pnpm verify
```

`pnpm verify` 故意不并入 `pnpm test`：它依赖服务器，而一个"服务器没开就失败"的测试套件，最终会被所有人学会忽略。它补上了单元测试补不了的那个缺口——所有单元测试喂给解析器的文本都是**本仓库自己写的**，所以一旦我们对真实 SSE 分帧的假设有误，全部单元测试都看不见。

## 隐私

这个扩展会读取网络载荷，所以策略是刻意设计的：

- **脱敏在页面内完成，发生在数据跨越任何边界之前**，并在 Service Worker 中再做一次。`authorization`、`cookie`、`x-api-key` 等始终被掩码；可在设置中追加 header 名称。请求体中的 Bearer/Basic token 以及 `sk-`、`ghp_` 之类的字面量同样会被掩码。
- **抓取结果只存在 `chrome.storage.session`**——内存支撑、浏览器关闭即清空、绝不落盘。即使脱敏之后，一次抓取仍可能包含凭据（一个意料之外的 header、载荷里的 session id），所以它不该活得比"当初值得收集它的那次调试"更久。
- **同一时间只抓一个标签页。** 钩子会注入到所有页面，但保持惰性，直到 Service Worker 为你打开侧边栏的那个标签页"布防"。切换标签页会显式解除旧页面的布防，因为页面在被告知停止之前会一直抓。
- **数据不出浏览器。** 无网络请求、无埋点分析、无远程代码。
- 申请的权限：`storage`、`tabs`、`sidePanel`，以及 `http`/`https` 的主机访问。**未**申请：`webRequest`、`debugger`、`scripting`、`unlimitedStorage`、`downloads`。

需要如实说明一个边界：`window.postMessage` 是公开通道，所以恶意页面可以**伪造**一条抓取记录。它无法读取记录，且 Service Worker 的 `tabId`/`frameId` 取自消息发送方而非载荷内容，因此伪造只能出现在制造它的那个标签页里。MAIN 与 ISOLATED 世界之间不存在私有通道；这是能力下限，而对一个调试工具来说是可以接受的下限。

## 能力边界

**支持：** 基于 `fetch`、`XMLHttpRequest`、`EventSource` 的 SSE 与文本流；当前标签页；主框架与 iframe。

**暂不支持：** WebSocket 与 WebTransport；跨标签页的历史归档；修改或重放请求；导入在别处录制的数据。每一项都是另一个工具该做的事，硬塞进来只会让这个工具把本职做得更差。

## 设计说明

### 为什么要替换页面自己的 `fetch`

MV3 没有给扩展任何读取响应体的途径：

| 方案 | 为什么不行 |
| --- | --- |
| `chrome.webRequest` | 只有 header。响应体从来没有暴露过，且 MV3 把它变成了只能观察。 |
| `chrome.declarativeNetRequest` | 设计上就是声明式的——能拦截和重定向，但永远无法观察内容。 |
| `chrome.debugger` / CDP | 能用，但会在标签页上挂出"正在被调试"的横幅，并与 DevTools 抢占会话。对一个需要常开的工具来说不可接受。 |
| 替换页面的原生 API | 唯一剩下的接缝。 |

因此由一个 `world: 'MAIN'` 的内容脚本在 `document_start` 时机替换 `fetch`、`XMLHttpRequest` 和 `EventSource`。

### 为什么必须刷新

钩子必须在任何页面脚本取得引用**之前**装好。一个在模块作用域执行 `const f = window.fetch` 的打包产物会永久持有原始函数，之后才到场的钩子什么也看不到。对于扩展启用之后加载的页面，`document_start` 能保证这一点——但已经打开的页面，脚本早就跑完了。所以需要刷新。

对于页面在自身启动过程中就发起的流，还有第二个问题：布防状态是异步到达的（MAIN 世界没有 `chrome.*`），此刻可能还没到。早期流量会先进入一个有界环形缓冲区，等答复回来后再冲刷或丢弃——否则最常见的那种情况（流式应用在加载时就发起请求）恰好会被漏掉。

### 钩子遵守的铁律

**页面的行为必须和没装这个扩展时完全一致。** 一个会改变被调试对象的调试工具，比没有工具更糟。具体来说：

- 用 `response.body.tee()`，绝不用 `response.clone()`。当两个消费者读取速度不一致时，`clone()` 会无上限地缓冲——在长连接的 SSE 上，这是用户页面内部的一处无界泄漏。而我们这一侧始终按网络速度排空，所以 `tee` 缓冲区几乎恒为零。
- 重建 `Response` 会丢掉 `url`、`redirected` 和 `type`——它们是原型上的 getter，构造函数没有对应参数。这些都被显式恢复，因为一个用 `response.url` 解析相对链接的页面，不该忽然拿到 `''`。
- 未被抓取的请求返回**原始对象**而非副本，这样恒等比较和非标准属性都能存活。
- 每一层包装都有守卫并回退到原生行为。这里出 bug 只会退化成"没抓到"，而绝不会变成"页面坏了"。

### 跟随当前标签页

侧边栏始终显示你正在看的那个标签页。切换标签页、切换窗口、关掉已布防的标签页，都会自动重新指向——没有"选中此页面"按钮，因为一个以"当前页面"为范围的面板，本不该需要别人告诉它当前页面是哪个。

这之所以安全，是因为抓取结果按**标签页**分别存储：切走只会解除该页布防，绝不会丢弃它已经收集到的内容，所以切回来就能恢复。

要让它可靠，需要两件很容易做错的事：

- **用端口，而不是猜。** Chrome 不会触发侧边栏关闭事件，所以面板在其整个生命周期内持有一个 `chrome.runtime.connect` 端口。它不传输任何数据；`onConnect`/`onDisconnect` 只是"现在究竟有没有面板在看"这个问题唯一诚实的答案。靠消息流量去推断，会让 Service Worker 无法区分"面板关了"和"面板只是安静"。
- **持久化布防状态。** MV3 会在约 30 秒空闲后回收 Service Worker，而 SSE 流在两帧之间的空闲远超这个时间。因此布防状态和抓取数据一起存放在 `chrome.storage.session`。没有这一步，一个在面板空闲期间被回收的 Worker 重启后会以为没人在看，进而拒绝为你接下来选中的标签页布防——面板会一直显示"未选中页面"，直到你关掉再打开。而持有端口本身也会在活跃会话期间让 Worker 保活，从根源上消除了大部分回收。

`tests/arm.spec.ts` 通过把状态用 JSON 往返序列化来模拟回收，因为该文件里其他每个测试都让同一个控制器走完单一连续的生命周期——而回收打破的恰恰正是这个假设。

### 页面消息按到达顺序处理

`handlePageMessage` 是 `async` 的：在触碰 store 之前，它要 await 设置、布防状态和标签页 hydrate。这些 await 都是挂起点，所以在没有队列的情况下，同一个标签页的多条消息会同时在飞，并以任意顺序恢复。

这是致命的，因为 store 是顺序敏感的：`stream.headers` 和 `stream.chunk` 要解析由 `stream.open` 创建的记录，而如果 `open` 尚未完成，它们什么也找不到。因此消息按**标签页**串成链——一个慢的标签页不会拖累其他标签页，但同一标签页的消息一定按到达顺序处理。

它造成过一个真实的、用户可见的 bug：在已经加载完的页面上抓取正常，导航之后就失效了。在启动过程中就开始推流的页面，其首批帧发出时 Worker 还在做首条消息的惰性初始化，那些 await 会真的挂起；而稍后才推流的页面 await 的都是已完成的 Promise，靠运气保持了顺序。实测到的恢复顺序是 `headers`、`chunk`、`open`——于是流出现在面板里，事件数为零。

与此相关，`CaptureStore` 现在会**统计**无法匹配到流的消息（`orphanCount`）。这个 bug 藏了这么久，正是因为那些丢弃是静默的；而一个会悄悄扔掉数据的调试工具，比一个承认自己扔了的更糟。

### 一次性的批量展开

"全部展开"和"全部收起"位于帧列表上方的吸顶工具栏，同时作用于事件行和每行内部的 JSON 树——只展开行却仍藏着载荷，那是半成品。

这个指令携带一个**nonce**，而不是布尔值，因为布尔值无法表达按钮所需的两半语义中的任何一半：

| 设计 | 会怎么坏 |
| --- | --- |
| 会锁存的 `forceOpen` 布尔值 | 覆盖之后所有点击，于是你手动收起某个分支后它立刻弹回展开 |
| 普通布尔值 + 监听变化 | 第二次按"全部展开"产生的值完全相同，什么都不会发生，按钮看起来坏了 |

nonce 让每一次按下都成为一个独立事件，每个节点恰好消费一次，随后把控制权交回本地状态。之后挂载的行会采用当前指令，因此流中途到达的帧与用户的选择保持一致。这条规则集中在一个导出函数 `resolveBulk` 里，这样树和行不会各自漂移。

批量操作只能触及当前已挂载的帧——长流是窗口化的——所以工具栏会明确写出数量（`80/2431`），而不是暗示它处理了全部。

### 不同传输方式的保真度

| 传输方式 | 抓到什么 | 局限 |
| --- | --- | --- |
| `fetch` | 原始字节 | 无——精确分帧、注释与心跳全部保留 |
| `XMLHttpRequest` | `responseText` 增量 | 文本无局限；`blob`/`arraybuffer` 类型会被报告为*不可读*，而不是被省略 |
| `EventSource` | 由已解析的 DOM 事件重建 | **注释与精确分帧无法获得**——字节先被浏览器消费了 |

界面会明确标注 `EventSource` 这种情况，而不是让你误以为服务端没发心跳。同样的原则贯穿配额裁剪：被丢弃的帧会被计数并报告，因为把有缺口的记录当成完整记录，会导出错误的结论。

### 不靠厂商映射表来合并增量

每家流式 API 嵌套增量文本的方式都不一样——`choices[].delta.content`、`delta.text`、`candidates[].content.parts[].text`、`response`，以及某个自研网关发明的任意结构。硬编码一张列表，对下一个 API 和所有内部 API 都会静默地什么都合不出来。

取而代之，合并会去**发现**这个字段：在一条流中，增量文本字段会在多数帧里出现于同一路径，而 id 或模型名只出现一次，`role` 则从不变化。已知字段名的权重高于未知字段——正是这一点避免了把推理模型的 `reasoning_content` 草稿当作答案呈现——其余则由覆盖率决定。

累积式风格（每帧都重复此前全部内容）会被单独识别并取最后一个值，因为把它们拼起来会产生平方级的垃圾。

面板始终显示它用了哪条路径，让推断可核对，而不是变成魔法。

### 测试说明

测试覆盖了按 WHATWG 规则校验的 SSE 解析器（BOM 处理、跨 chunk 断开的 `\r\n`、裸 `\r`、`id` 中的 NUL）、脱敏、配额淘汰、布防状态迁移、针对真实 OpenAI/Anthropic/Gemini/Ollama 结构的增量发现，以及钩子的页面保真承诺。

有两个测试的存在纯粹是因为少了它们就会藏住真实 bug：

- **Response 恒等性**——未被抓取的请求必须返回同一个对象引用，而不是一个等价副本。
- **XHR 增量**——`responseText` 是累积的，每次 progress 事件整体转发会让每一帧显示 N 次。

#### 单元测试不够

`tests/worker-lifecycle.spec.ts` 会把**真实的** `background/index.ts` 跑在 `tests/harness.ts` 上——一个会真正派发事件的 `chrome` 替身：标签页切换、窗口焦点变化、端口连接、导航、Worker 回收。

它之所以存在，是因为"切换页面后抓不到"的报告出现时，316 个测试全是通过的。那些测试全都**直接**测 `CaptureStore` 或 `ArmController`；从没有任何测试执行过把它们接到 Chrome 生命周期上的那个模块，于是接线层的所有 bug 都是隐形的。旧的 `tests/fake-chrome.ts` 甚至把 `addListener` 存成空实现，这让盲区成了结构性的，而非偶然的。

这个替身有两处是承重的：

- **`sendConcurrently`** 投递消息时不等待每条回复，这才是 Chrome 真实的行为。逐条等待会把 Worker 的处理器串行化，掩盖所有顺序 bug——最初那个故障只有在真实交错下才能复现。
- **`evict()`** 丢弃监听器但保留存储，于是 Worker 回收可以被测试，而不是靠推理。

用这种方式找到的 bug，每一个都在相应代码处留了注释并写明失效模式：一处脱敏泄漏、一次增量排序错误、被回收弄丢的布防状态，以及乱序处理的页面消息。

#### 伪造的浏览器也不够

`pnpm e2e`（`demo/browser-check.mts`）会启动真实 Chromium 加载真实的解压 `dist/`，打开面板，并在导航与切换标签页的过程中断言面板实际收到的状态。伪造的 `chrome` 对象编码的是我们**对 Chrome 的信念**；只有真实浏览器能推翻它们。

它当场推翻了我两个信念：

- 面板页面和 Service Worker **不是**可互换的消息对端。`chrome.runtime.sendMessage` 永远不会投递给发送方自己的上下文，所以 Worker 问**自己**要状态会得到 `undefined`——再配上 `?? 兜底值`，读起来就成了"什么都没抓到"，让每一条断言都因一个并不存在的原因而失败。
- Playwright 的默认参数 `--disable-extensions` 会静默压过 `--load-extension`，而稳定版 Chrome 151 干脆完全忽略该参数。两者都是**静默**失败：Chrome 正常启动、不报错、什么也不加载。更糟的是，此时 `serviceWorkers()[0]` 返回的是某个**内置**组件扩展的 Worker，于是一个天真的"Worker 已启动"检查会在扩展根本没加载的情况下通过。因此该脚本改为按 manifest 名称识别自己的 Worker。

也要说清这个脚本**做不到**什么：把按标签页排队的修复还原之后，它依然全部通过。它忠实地演练了导航和标签页切换，但本地托管的页面无法稳定复现顺序 bug 所需的启动时序窗口——请求完成得太快，Worker 的惰性初始化来不及交错。真正钉住那个故障的是单元层的 `sendConcurrently` 测试。两层都必要：浏览器证明接线是真的，替身证明顺序是对的。

#### 一个值得写明的偶发失败

Vitest 默认的 fork 进程池在 Windows 上会偶发地在**任何测试开始之前**就死于 `VirtualAlloc failed` 或 `spawn UNKNOWN`，表现为一个没有失败测试的裸 exit 1。正因如此 `vite.config.ts` 里设置了 `pool: 'threads'`。

在内存压力很大时（例如残留了大量浏览器进程），线程也可能被饿到让一个纯同步断言报出约 6 秒耗时并失败。那是环境问题而非代码问题：它无法复现，且涉及的断言完全不碰计时器。
